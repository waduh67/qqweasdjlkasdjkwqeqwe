# F2 targeted draft-expiry design review

Source baseline: `d8a4ae2909c87619c24488e486905c263add44b8`, validation worktree. Read-only design review; no product edits or runtime QA. This is a recommendation, not implementation acceptance or final F2 approval.

## Recommendation

Use **(b) an append-only, tenant-scoped terminal expiry decision**, with database command guards and a common explicit `EXPIRED` read projection. Keep the original document/line/material-plan/specialized request/approval snapshots unchanged. Expiration must prevent new execution, not merely add an audit note. Apply it to every retained idle family in F1, including unapproved immutable proposals and superseded unsubmitted plan snapshots.

Option (a), changing stored document state to `EXPIRED`, can be made correct but has substantially more guard surface here. The existing `warehouse_document_guard()` lifecycle and state CHECK reject that transition; leaving DRAFT normally invokes physical-dimension requirements. `warehouse_sealed_material_plan_guard()` permits only DRAFT→SUBMITTED for sealed plans, while `warehouse_assert_material_submission()` treats a non-DRAFT plan as submitted. Specialized deferred request guards bind exact revision-zero document and line snapshots, later extended only for their specific posted/rework effects. Adding a generic state exception risks weakening those bindings. An external decision preserves them without a generic guard bypass.

## Minimal terminal record and enforcement

- Add a forward migration (next available after immutable V178.9; coordinate numbering with concurrent draft-edit work), with FORCE RLS, tenant `USING`/`WITH CHECK`, composite target references, append-only protection and one terminal record per document or material-plan identity. Prefer separate typed document/plan targets over an unchecked polymorphic ID. Persist source revision, last-activity/deadline/policy, decision timestamp and reason. The database must verify them under the target row lock; clients cannot choose an earlier deadline or expire another tenant's resource.
- A persisted policy and authoritative database time must define idle TTL. Do not derive it from browser time or let list/detail reads or command replay renew it. The plan has no numeric TTL, so document the chosen value. A due source must reject new work even if the scheduler has not run. Genuine successful draft editing before expiry can establish a new deadline; an expired identity never revives.
- The expiry insert must lock/recheck a retained DRAFT with no applied effect, physical operation, submission or stock reservation created by that source. Ordinary draft-command receipts are not physical effects: a blanket `NOT EXISTS inventory_operation` would incorrectly exclude saved receipt/transfer/count drafts. No movements, balance updates, reservation release, custody/title/assignment changes or admission effects belong in expiry.
- Use a common SQL assertion on new document execution and draft mutation, not solely service checks. Hook document UPDATE/DELETE, document-line INSERT/UPDATE/DELETE, mutable intake/binding/settings children, plan submit/line mutation and approval/effect creation. A terminal source must remain immutable even though its stored source state is still DRAFT. Existing immutable history checks remain intact.

`DurableApprovalService.terminate()` can advance a SUBMITTED count to RECOUNT_REQUIRED. Generic draft expiry must only select DRAFT counts; it must not repurpose approval expiry to expire COUNTING/SUBMITTED counts or alter observations.

## Coverage of retained families

- Ordinary documents: RECEIPT (including supplier replacement receipts), TRANSFER, COUNT.
- Separate sealed plan identity: every unsubmitted `inventory_material_plan`, including superseded drafts; show history as expired without making an older plan current.
- Immutable approval proposals: LOSS, SCRAP, DISPOSITION_REVERSAL, ASSET_LOSS, TITLE_CORRECTION, RETURN_TITLE, ADJUSTMENT discrepancy and OPENING_BALANCE. Their specialized source snapshot/request tables remain append-only. Pending approval does not grant an indefinite exemption: when the chosen idle policy expires the source, atomically terminate pending approval without executing the effect.
- Do not target transient DRAFTs that are posted in the creating transaction, submitted DEMAND, PICKED/UNPICKED ISSUE, COUNTING/SUBMITTED COUNT, in-transit returns/transfers/RMA, inspection/repair or active assignments. Those have explicit physical lifecycle protocols.

Specific immutable guard families demonstrating why source-state mutation is broader: `warehouse_assert_disposition_request` (V175.138/.139), `warehouse_assert_compensation_request` (V175.140/.141), `warehouse_assert_asset_loss_request` (V175.143/.144), `warehouse_assert_return_title_request` (V175.131/.132), `warehouse_assert_replacement_request` (V175.134/.135), and `warehouse_migration_opening_guard` (V177.6). Keep their source/effect invariants rather than adding an early return when expiry exists.

## Read/UI and race requirements

Use one effective-state predicate for list filtering, counts, detail, approval source display and eligibility. Existing receipt/count/transfer readers decode stored states into enums, while specialized readers often return a saved original body or infer DRAFT from absence of an effect. Every such path needs the terminal overlay, typed EXPIRED handling and an expired timestamp/reason. Leave original idempotent response bytes and approval source snapshots intact. Replaying an authorized historical successful create/edit returns its original receipt; current detail supplies EXPIRED and new commands return a stable conflict such as `DRAFT_EXPIRED` with a reload/new-draft action.

Serialize expiry versus edit/approval on the same document or plan row. With the tenant authority change fence first, existing application command fences serialize safely; SQL row locks must also protect direct guarded writes. If a valid edit wins before the deadline, recheck the new revision/deadline and do not expire its old version. If expiry wins, all new mutations/approval/effects fail. If final approval wins while still eligible, expiry must observe the posted/effected source and skip it. Use database time after lock waits, and preserve stored replay responses during recovery.

Required proof: each listed family expires with unchanged physical facts and immutable original snapshots; due commands fail while the scheduler is stopped; pre/post-deadline edit and approval races have one valid outcome; direct non-owner SQL cannot bypass terminal guards; expired latest plan does not resurrect its predecessor; list/detail/filter/UI agree and original replay is unchanged. Existing approval-expiry cases alone do not prove these properties.

## Concrete refinements from the remaining source inspection

**Locking:** `warehouse_approval_decision_binding()` currently locks the approval at V175.7 line 6. Do not append a source-locking expiry check after that statement. Obtain an unlocked approval preview, lock its source, then re-read/lock the approval, matching `decideLocked` and expiry's source→approval order. The existing source-owner locks and topology order remain in the application path. Under the scheduler's exclusive authority fence, do not then call an API that attempts to obtain a current-user fence. New SQL expiry protection belongs in the BEFORE command/write phase; a deferred historical binding check must not invalidate a past decision merely because wall time later passes.

**Child mutations and physical admission:** `warehouse_receipt_intake_guard` (V174.12) locks the document and accepts stored DRAFT; add terminal/liveness validation there. Include `warehouse_transfer_binding_guard` (V175.113) and `warehouse_count_scope_guard` (V175.114), plus the forward count-edit child guards introduced by the separate PUT work. Otherwise an external terminal decision leaves the old stored-DRAFT checks satisfied. `PostingDocuments.lock()` is the common locked posting entry and can reject a new post from an expired/due target; the database document transition guard remains the final atomic backstop. Preserve all existing specialized effect bindings. Do not add a generic early-return exemption to those bindings.

**History versus liveness:** `MaterialPlanningStore.current/get/history` explicitly calls `warehouse_assert_material_submission`; that function is an integrity check also used by readers. Keep valid expired DRAFT snapshots readable, and reject submit in the submit/write path. Likewise, keep `WarehouseApprovalStore.source()` returning the original content for audit/hash comparison; carry effective terminal status separately. `WarehouseApprovalQueryService.source/details/locked` and `WarehouseApprovalQuery.candidates` need the expiry predicate in request/decision/rework eligibility and terminal list filtering. Preserve `details.document` as the sealed approval-time document and expose its existing current-source state field as EXPIRED, rather than altering the displayed sealed snapshot silently.

**Specialized projections:** `WarehouseDispositionStore`, `WarehouseCompensationStore` and `WarehouseAssetLossStore` decode stored state and give rework disposition precedence; effective expiry must take precedence in the current projection. `AssetTitleCorrectionStore.find/get` returns the immutable snapshot; `ReturnReacquisitionStore.list` presently exposes source revision 0 and an optional applied revision without a terminal state; `SupplierReplacementStore.list` overlays only replacement identity on the original saved view; `MigrationOpeningStore.list` reads document state while `get` returns original_body. Add explicit current terminal metadata to these read DTOs without modifying replay responses. For `ADJUSTMENT`, update approval source/current status and `WarehouseTransferDiscrepancyStore.recoveryBlock`: an expired unexecuted proposal must allow a new corrected report once no pending/effected approval remains, while preserving the parent transfer remainder.

**Actual client contracts:** server enums in `WarehouseDocumentContracts.kt` and `WarehouseDispositionState`, web `receipts.ts`, `counts.ts`, `transfers.ts`, `dispositions.ts`, asset-loss/compensation/specialized read decoders and material summary/history must accept the chosen expired projection. `transfers.ts:31` specifically treats every non-DRAFT state as already dispatched and requires received+transit+resolved=requested: simply adding EXPIRED to the enum would still reject an expired never-dispatched draft. Treat EXPIRED as a pre-dispatch terminal state for this invariant and labels. Receipt/transfer page fallback text currently implies completion or in-transit stock for non-DRAFT values; provide explicit expired/no-stock-effect text. Add an expiry block in approval source/actions, and map the stable conflict in `web/src/api/warehouse/errors.ts` with reload/new-draft recovery. `WarehouseCommandJdbc` currently maps every SQL 23514 to SOURCE_NOT_VERIFIED; use an identifiable constraint/code mapping for DRAFT_EXPIRED, not raw exception text exposed to users.

**Transaction and privacy:** an action that inserts the terminal row then throws inside the same transaction will roll that record back. Either let a pure due/liveness check reject and the bounded scheduler persist the decision, with read projections also treating the due deadline as terminal, or use an explicit outer recovery transaction that commits the expiry/conflict receipt. Do not use a nested independent transaction while holding the source fence/row. Keep permission/tenant/warehouse/area checks before returning expiry-specific information; expired history retains the same visibility rules and cannot expose a hidden source ID. Authorize original replay under current scope before returning its unchanged stored response.

This completes the targeted design review. No C7 expiry requirement or specialized family is waived. Implementation and runtime race/schema/UI proof remain required.
