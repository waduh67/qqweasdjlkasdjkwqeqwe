## Targeted schema findings and minimal persistence change

Path prefixes in this section: `S/` = `server/src/main/kotlin/com/duluin/ftth/`; `M/` = `server/src/main/resources/db/migration/`.

- `M/V175_114__warehouse_blind_count_sessions.sql:25`–30 installs `warehouse_count_immutable` (generic append-only) on **scope, entry and round** tables. Updating location or deleting old assignments will fail today. Replace only scope/entry mutation guards with tightly constrained pre-start draft guards; **retain round immutability**. Scope UPDATE may change location and supported partial flag only; preserve ID/tenant/created timestamp. Entry replacement can use DELETE + INSERT; no need to permit arbitrary entry UPDATE. Every permission must require owning document `kind=COUNT`, `state=DRAFT`, no rounds/observations/result/approval/posting, and correct tenant scope under the same document lock. Never enable these mutations in COUNTING/RECOUNT_REQUIRED/SUBMITTED/APPROVED/POSTED.
- The same migration's `warehouse_count_scope_guard:65`–94 already checks insert lifecycle and matches each count entry to its canonical balance dimension and scope. Keep those checks, strengthening any missing complete unit/segment binding validation rather than accepting client dimension fields. `M/V174__warehouse_documents_and_balances.sql:302` `warehouse_line_guard` permits line replacement only while parent is DRAFT and requires line.document_revision to equal parent revision. Preserve it. `inventory_count_entry.id` references the document-line ID without cascading delete, so delete entries before their lines; allocate fresh line IDs at the new draft revision.
- Add/reuse a COUNT-specific header guard that allows only reason/revision/updated timestamp for a DRAFT→DRAFT edit; original actor, tenant, ID, code, kind, creation and original history stay fixed. Existing generic DRAFT handling is not sufficient authority to rewrite owner metadata. Apply a narrowly scoped final-state guard for create/update that validates the new immutable command receipt/input against the final scope/entry/line set and next revision, rejecting missing command, empty/incomplete replacement or fabricated snapshots. Validate authoritative current command against current rows; do not compare older immutable draft receipts against today's changed scope/assignments.
- Minimal transaction mutation order, after all authorization/locks/replay checks: remove old entries then old lines; increment header revision once while DRAFT; update existing scope; insert the complete server-derived line set at the new revision; insert assignments; record original response/canonical command; let final guards validate the complete result before commit. No movement, reservation, stock balance, count round or observation is written. A failure rolls everything back. An immutable snapshot table is not automatically needed if existing operation receipt + canonical identity retain the entire input and original response and final guards bind the current state correctly.
- `M/V175_114__warehouse_blind_count_sessions.sql:37`–63 makes observations immutable and binds them to the current assigned dimension/round. `M/V175_114_3__warehouse_count_observation_command.sql` binds observations to command receipts. `M/V175_114_1__warehouse_count_approval_binding.sql:33` validates complete outcomes, counts every assignment and checks independent approval; all must remain intact. Their revision arithmetic is relative: editing to revision N then starting at N+1 is valid. Do not reset revision/round numbering to zero or hard-code the first round as 1.

## Command, replay and scope requirements

`S/inventory/application/service/WarehouseCountService.kt:148` (`mutate`), `adapter/outbound/persistence/WarehouseCountStore.kt:15` (`get`), and `WarehouseCountReceipts.kt:10` are the existing integration points.

1. Add `replace(id, input, key)` to `InventoryCountApi.kt` and PUT `/{id}` to `WarehouseCountController.kt`; use strict `WarehouseReceiptJson.decode` and reject actor/tenant/book quantity/source authority fields. Separate `WarehouseCountDraftUpdate(expectedRevision, locationId, partialLocation, reason, entries)` avoids changing create's contract. Preserve the 1–100 distinct balance-ID bound, reason limit, partialLocation=true contract and overflow-safe revision limits.
2. Use one transaction with cutover → current authority → topology → owner document → deterministic selected balance/dimension locks. Preserve current requester ID; an assigned counter is not allowed to edit scope/counters/reason. Require current count.view/count.manage, and access to both existing location and proposed location. Revalidate every selected position as VERIFIED/active, matching the new location, canonical stock identity/SKU/unit/owner/condition/custodian; no draft quantity comes from the client. Lock stock in the same deterministic order used by existing count operations and do not introduce opposing lock order with posting.
3. Counter validation should share the eligibility predicate with `WarehouseCountQueryService.kt:53` (`counters`): active same-tenant user, count.view+count.manage and current location/area coverage. That query is currently stricter than `WarehouseCountService.create`, which only checks count.manage in the directory. Reuse one authoritative eligibility helper for create/update/query so the API cannot assign an ineligible counter merely because the picker filtered them out. Recheck it under the authority fence, including retained assignments.
4. Canonical hash = requested document ID plus full input including expectedRevision, with stable JSON normalization; do not hash mutable live names/quantities. Use namespace `warehouse.count.update` and business action `COUNT_UPDATE`, result revision N+1, status 200, and the actual original response stored through `WarehouseCountReceipts`. Same key/same payload returns that response; changed payload/ID fails; a different key with stale expectedRevision fails without another revision. Validate resource/actor before returning or locking an unrelated command resource.
5. Replay must reload current authorization **before** returning history. Once editing can move a count from location A to B, existing `replay` checks only the current session location. That is insufficient for an old create/update receipt containing A. Authorize both current resource scope and the scope disclosed by the original stored response/canonical command (and original actor), without rebuilding the response from mutable current state. Audit both create and update replay after scope changes/revocation; do not accidentally leak old location/counter information or return a new body for the old key.
6. Check DRAFT, expected revision, no round/facts/result/approval/movement under the owner lock immediately before mutation. Replays of previously successful edits may still return their original response after start if currently authorized; a *new* edit after start is rejected. C7 expiry must take the same lock/fences and win or lose atomically against update/start. Do not revive an expired draft or erase a round.
