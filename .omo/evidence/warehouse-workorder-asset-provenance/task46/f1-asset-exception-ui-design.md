## Contract applicability and minimum delivery

The plan does not literally require a button called `ASSET_LOSS` or `TITLE_CORRECTION`, nor a dedicated page for either. Task 41 explicitly lists install/replace/remove/handover. However, task 21 requires independently approved post-handover title corrections, task 28 requires recovery obligations to close by actual recovery or approved loss, and task 37 exposes the task 28 exception/approval workflow. C9 requires working screen actions and actionable failure states; the scope guard rejects a missing-action UI presented as delivered WMS. These requirements together make an authorized, discoverable creation path necessary for these supported operational exceptions. API-only creation with manual UUID collection is not sufficient evidence of the complete visible workflow. This is a whole-flow interpretation, not a claim that the plan names two particular widgets.

Current approval UI already understands both document kinds, displays typed effects and can request independent approval from a source document. It does not create the source proposals. Current `CustomerAssetPanel.tsx:42` exposes only handover/replace/remove/relocate. Searches of `web/src` found no command caller for either `/api/v1/warehouse/asset-losses` or `/api/v1/warehouse/asset-title-corrections`.

Minimum placement: two named proposal actions in the existing customer asset row, beside its provenance/title history, opening a small form and existing `WarehouseCommandDialog`. After successful creation, link to `/warehouse/approvals?sourceDocumentId=<returned document id>`. Existing independent approval, sealed evidence, history and final effect UI can finish the workflow. A separate loss dashboard, generic correction console, new financial workflow, arbitrary owner/asset reassignment, portal action or mobile-native feature is optional expansion, not required by this finding. Existing warehouse stock/customer links may optionally point to the same context-bound form.

## Read/API dependencies that a working form must satisfy

1. `GET /api/customers/{id}/assets/ownership` already returns `CurrentAssetOwnership`, including handoverId, current assignment/title revisions, current owner and original WO. The existing web history row has revisions and handover **state**, but lacks handoverId. Use the actual ownership read or an additive context DTO; never infer a handover UUID from assignment, signature or origin IDs. Match customerId/assignmentId/assetId/workOrderId to the selected named history row. Its `positionStatus` currently has a default in the DTO; server-side current-position validation remains authoritative.
2. Present named customer, SKU/serial, original WO, current owner, origin and signer/date. Do not ask the operator to type opaque assignment/WO/handover/evidence IDs or revisions. The ownership list is currently unpaged; a selected-assignment context read is preferable if adding a read endpoint, and avoids a new broad search surface.
3. Existing `getAssetJob` is unsuitable for a general office requester: `S/workorder/adapter/outbound/persistence/WorkOrderAssetWorkbenchAdapter.kt:47–70` requires a current assigned technician with `customer.onu.assign` and `workorder.order.field`. The new actions must not sit under the existing panel's `manage = assign && field` gate. Title creation requires `inventory.approval.request` and `.view`; loss creation requires `inventory.custody.manage` and `inventory.approval.request`. Customer context still requires customer view/area access, and source/destination warehouse scope remains enforced.
4. Both creation services call `AssetHandoverWorkOrderPort.signature`. The actual adapter (`S/workorder/adapter/outbound/persistence/AssetHandoverWorkOrderAdapter.kt:58–78`) verifies a committed active signature and its object digest, then calls the owner evidence API. `S/workorder/application/service/WorkOrderEvidenceService.kt:232–238` requires `workorder.evidence.view`, or a currently assigned field technician, in the WO area. An approval-only requester is therefore not automatically authorized to create these proposals. UI prerequisites must state this actual evidence-access dependency, or a deliberately scoped owner read capability must be provided and validated. Do not silently broaden general WO evidence access or reuse an approver's capability for a requester.
5. The loss form also needs the original WO's current warehouse revision. The ordinary `WorkOrderView`/`WorkOrderDetail` (`S/workorder/application/port/inbound/WorkOrderQuery.kt:41–89`) does not expose that field. A narrow owner-derived exception context read can supply the revision plus named WO and eligible committed signature, after authorizing the selected customer/assignment and request role. Keep owner-module boundaries; inventory should not query the work_order table. Signature retrieval must use the same committed/current reference that the command validates, not an arbitrary historical signature UUID or generic receipt attachment. A new evidence-upload system is not needed for this UI gap: reuse the existing authorized WO evidence workflow and show its missing-evidence next step.
6. Before confirming, reload selected assignment/title/evidence/WO context and reject changed or inaccessible choices. Keep the original command key across response-loss retry; changed payload needs a new command after explicit review. On stale/permission/source errors show a reload/appropriate flow, without applying a local title or loss result. Disable server actions offline/read-only/pending. Show successful proposal reference and approval next step; where approval.view is unavailable, explain that an authorized requester/reviewer must continue rather than show a broken link.

## Supplier replacement: authoritative editability

`ReceiptView` (`S/inventory/application/port/inbound/WarehouseReceiptModels.kt:44`) exposes state, revision, receipt content and costVisible, with no replacement/editability discriminator. `web/src/api/warehouse/receipts.ts:50` mirrors that omission. `WarehouseReceiptsPage.tsx:92` offers `Ubah draft` for every managed DRAFT with the requisite cost/master reads. `WarehouseSupplierReplacement.tsx:44` says `Masih draft`, reinforcing a misleading edit expectation for a sealed proposal.

The domain fact is the tenant-scoped relationship in `inventory_repair_replacement_request` by receipt_id. `S/inventory/adapter/outbound/persistence/SupplierReplacementStore.kt:33` already returns the exact record; `WarehouseApprovalStore.isReplacement` independently uses the same relationship. `SupplierReplacementService.kt:56–64` creates the receipt then seals its source/title/repair/content snapshot. Use this relation to derive an additive receipt purpose/discriminator such as `ORDINARY` / `SUPPLIER_REPLACEMENT`, or a domain-only `draftEditability` reason. Compute it for current GET/detail/list in `WarehouseReceiptService.view`, separate from actor permissions and cost visibility. No schema migration is necessary merely to expose an existing relationship.

Minimal boolean alternative: `draftEditable = state == DRAFT && !isReplacement(receipt.id)`, explicitly meaning domain editability, combined by the UI with its existing permission/cost requirements. An enum or nullable replacement context containing returnId is more useful because it gives an explanation and a safe link to the return case for a corrected successor proposal. Expose only references permitted by the current read scope; do not leak the full sealed replacement/evidence snapshot. Do not derive this from externalReference text, operation-key prefix, cost presence, legal owner, revision zero, or a guessed customer/WO field. Ordinary and replacement receipts share those incidental properties.

For sealed replacement DRAFTs, remove the ordinary edit affordance and its cost-edit warning, label them as recorded replacement proposals awaiting the applicable receipt approval/receive workflow, and link to the existing return case to prepare a new corrected request when the old one is rejected/stale/expired and the source is still eligible. Retain independent approval/receive/inspection steps; hiding `Ubah draft` must not imply the proposal is posted. The server must reject direct ordinary PUT with a stable domain error even if a stale client renders the button; the immutable database guard remains the final protection. Do not mutate the snapshot to make an unsupported generic edit work.

Original replay bodies may predate the additive field. The receipt parser already handles this for snapshot names and cost visibility (`receipts.ts:55–57`): missing editability must fail closed for the edit button until a fresh authorized GET, never default to editable. Creation responses generated inside the replacement transaction can precede the relationship insert; the final reloaded GET must determine the persisted purpose.
