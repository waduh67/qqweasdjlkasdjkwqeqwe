# F4 targeted expiry clock/deadline design

Design-only source review at `d6baf827ce9bcdae6222acc7c63b8fe64b89fa87`. No product edits or QA. This supplements `f2-draft-expiry-design.md`; it does not accept an implementation or grant final F4 approval. Next migration observed:178.12, subject to a fresh inventory check before writing it.

## Requirement versus design choice

C7 explicitly requires idle drafts to expire without stock effects, append-only audit, tenant/RLS/composite-reference protection and a non-owner/NOBYPASSRLS application role. C3 requires original-response replay and current authorization; C8 requires stable conflicts and server-derived fields. The plan does **not** choose a seven-day draft TTL, per-tenant draft policy configuration, a particular clock table or a public policy-management UI. Those are implementation choices. The existing versioned approval-policy expiry requirement does not itself prescribe a separate draft-policy API.

**Recommendation:** keep the proposed append-only terminal expiry overlay, add one protected activity/deadline stream, and use a small owner-managed versioned tenant policy table. This is a good minimal fit for the current source because it does not mutate sealed proposal/header snapshots or repeatedly reopen their JSON guards. A DB-maintained mutable deadline column could also be correct in isolation, but would require more changes across the current immutable header/request guards; an extra mutable “current activity” table is unnecessary. No public settings flow, lease service, heartbeat endpoint or fake-clock switch is needed.

## Why header timestamps are insufficient

V174's `warehouse_document_guard` returns immediately for a same-state update, and V178.10 and V178.11 deliberately exclude `updated_at` from their draft binding comparisons. A valid raw draft revision can therefore supply a future timestamp. Even a default of `clock_timestamp()` is caller-overridable. Existing operation/snapshot timestamps are also application-supplied or defaulted; their immutability is not proof of authoritative wall-clock stamping.

Do not use any of these values for new liveness decisions. Never accept a request/SQL helper argument for activity time, deadline, TTL, policy version or clock override. Use a protected trigger's `clock_timestamp()` after the source lock is held. `now()`/`transaction_timestamp()` preserve transaction start, and `statement_timestamp()` precedes lock waits, so neither is sufficient for command expiry.

## Small persistent model

1. **Policy versions:** `(tenant_id, version, ttl_seconds, recorded_at)` with a composite key, positive finite bounded TTL, immutable old versions and DB-stamped audit time. Seven days (`604800` seconds) is a reasonable chosen default, explicitly document it as a choice. Select the latest committed version when a target is first created, and pin that version/TTL for that target's lifetime. Subsequent owner policy versions affect new identities only. This avoids retrospective deadline extension, shortened deadlines and extra policy-lock ordering in ordinary commands. A new valid material-plan identity may use the newer policy; its expired predecessor remains expired.
2. **Activity:** an append-only row containing target identity, qualifying source revision, policy reference/TTL, DB-observed time, effective activity time, absolute deadline and provenance (`CREATED`, `DRAFT_SAVE`, `LEGACY_`d6baf827ce9bcdae6222acc7c63b8fe64b89fa87``). Use separate typed document/plan tables, or one table with exactly one of `document_id`/`plan_id`, two composite tenant FKs and separate unique indexes. An unchecked generic UUID/type pair is insufficient. Unique `(tenant,target,qualifying_revision)` prevents duplicate renewal. Do not reference the mutable document revision with an FK; past activity must remain valid after later revisions.
3. **Expiry:** one append-only terminal decision per target identity, referencing the exact activity row/deadline and source revision observed under the source lock. Its insert guard derives these values and checks actual DB time, eligible unposted source and absence of an existing terminal decision. It must never trust caller-chosen timestamps. The decision cannot be undone by new activity, policy changes or rework.

For sealed material plans, the target is the immutable plan ID and its `plan_revision`, not the work-order ID or mutable row revision used for submission. Replacing a plan creates a new ID; old unsubmitted identities keep their own clocks. `MaterialPlanningStore.current()` must still select the largest plan revision, even when expired; do not fall back to an older live plan or reset revision numbering.

## Define renewal narrowly and enforce it atomically

Create the first activity automatically with the target. Renew only an accepted explicit versioned draft save for editable RECEIPT/TRANSFER/COUNT. An explicit save may keep the same business values; the accepted new command/revision is the activity. Reads, idempotent replay, policy changes, attachment listing, approval polling, scheduler work, status decoration and repeated failed commands must not renew it. Keep immutable proposals and sealed plan IDs on their creation deadline unless an explicit separately justified user action is intentionally defined to renew them.

**Do not stamp every revision change.** `WarehouseApprovalStore.reworkDisposition()` changes DRAFT revision and `updated_at` for approval rework; these system/control changes must not silently get another full TTL. Likewise, a header-only raw revision increment or same-revision child rewrite is not an accepted draft save. Bind renewal to the expected save namespace/action/revision and immutable command identity; a deferred structural check can verify the command written later in the transaction. If those references are missing, the transaction must roll back or receive no renewal. Do not use a deferred wall-clock check for this structural seal.

For a save, lock the source, load its trusted previous activity, then evaluate `clock_timestamp() >= old_deadline` and terminal status **before** admitting a new activity. If due, reject; never create fresh activity and then test its fresh deadline. Only a valid pre-deadline save yields `activity_time = sampled_DB_time`, `deadline = activity_time + pinned_TTL`. Initial source INSERT and DRAFT UPDATE can use protected automatic row triggers; ensure creation's FK ordering is valid. An AFTER UPDATE trigger can reject and roll back the update while still holding the row lock. Trigger ordering and same-transaction command sealing must be explicit; no session GUC handoff is needed.

Guard child writes too. Receipt replacement currently deletes old lines before incrementing its header (`WarehouseReceiptPersistence.saveDraft:29`), so a header-only expiry check is incomplete. Intake, lines, count scope/entries and all other mutable children must lock/check the existing source deadline before writing. A later header renewal that misses the old deadline rolls back the entire replacement. Child operations within an accepted revision must not each append activity or extend its deadline. Missing activity on an eligible retained source is an integrity error, never a lazy “start now” reset.

## Privilege and tenant boundaries

The application should have SELECT only on policy/activity and no direct UPDATE/DELETE/INSERT/TRUNCATE authority. Terminal decisions can use a narrowly validated insertion function rather than unrestricted inserts. The automatic activity writer needs a hardened SECURITY DEFINER trigger function if its target table is SELECT-only for the caller. Revoke public/direct execution of trigger/internal helpers, use a fixed trusted search path and schema-qualified objects, derive scope from immutable trigger rows and explicitly call the tenant-scope assertion. The QA migration owner is BYPASSRLS, so a definer's explicit tenant checks matter even with FORCE RLS. Trigger invocation can work without granting ordinary callers direct function execution.

Explicitly revoke inherited DML/TRUNCATE/default grants: `test-environment.sh:151` and `database-fixture.sh:31` grant new owner-created tables application DML by default. Include FORCE RLS USING/WITH CHECK, composite target/policy/activity references and immutable identity guards. Do not give the app owner membership or trigger-disabling capability. Harden new tables/functions in production and the owned test databases alike.

A lazily initialized default policy avoids creating unnecessary rows for every empty tenant. If policy rows are eagerly seeded, or an otherwise empty tenant is configured, preserve the user's empty-tenant deletion behavior. V178.9 currently permits only two initialized control-row cascades. A policy-only control row needs an explicit equivalent cleanup decision; activity/expiry/business history must remain protected and block destructive deletion. Do not broadly cascade the new audit records.

## Deadline and lock semantics

Use one predicate everywhere: persisted expiry OR (eligible retained source AND trusted deadline <= current DB time). Equality is expired. SQL command guards enforce it even when the scheduler is stopped; reads can show effective EXPIRED while the scheduler later records the terminal decision. Keep integrity/history readers and authorized original-response replay usable. A check that inserts expiry then throws in the same transaction will roll its insert back; either use pure due rejection plus scheduler persistence, or the existing explicit outer recovery transaction. Never open a nested independent transaction while holding the source lock.

Preserve cutover → authority → existing owner/WO/topology fences → source → approval → stock order. In particular, `warehouse_approval_decision_binding` currently selects the approval FOR UPDATE at V175.7:6: obtain an unlocked source preview, lock the source, then lock/re-read the approval. Appending a source lock after that existing approval lock reverses order. A BEFORE UPDATE row trigger cannot undo the approval tuple lock already taken by UPDATE; normal SQL writers must acquire source first. Do not add late source-locking liveness calls to generic approval status updates merely to duplicate checks already done by the request/decision/effect entry paths. Raw inverted-order transactions may deadlock and roll back, but must not commit an effect; map that conflict consistently.

Recheck DB time after waits and at the locked admission boundary for each new save/submit/start/dispatch/approval effect. `PostingDocuments.lock()` is useful for an early rejection, but `WarehousePostingPersistence` subsequently waits on stock locks before `documents.advance`; the late transition/effect admission guard is necessary too. Use the same rollback/recovery behavior as approval expiry when a final approval cannot post. Once an action has been validly admitted and atomically completed, later wall time must not make its immutable decision fail a deferred historical integrity check. Define the admission point explicitly rather than relying on an earlier service read or caller timestamp.

Expiry versus edit uses the same source lock: a valid pre-deadline renewal wins and the worker re-reads that activity; an already-due source cannot renew even if the worker has not yet inserted a decision. If an effect wins, expiry observes the completed/effected source and skips it. Source DRAFT alone is insufficient for specialized proposals whose effect may be recorded separately: reuse family-specific effect/submission/physical-state checks, not `NOT EXISTS inventory_operation` (draft receipts themselves are operations). Expiry must never release reservations or mutate stock/custody/title/assignments.

A persisted terminal decision is irreversible even if host wall time moves backward. A purely computed “due” state before persistence assumes an operationally stable authoritative DB wall clock; `clock_timestamp()` is not a monotonic clock. Do not claim a stronger clock guarantee. Persisting observed terminal decisions can close that exceptional read-only observation gap; a cluster-wide monotonic clock ledger would be additional scope, not a C7 requirement established here.

## Bounded upgrade baseline

The migration cannot reconstruct trustworthy past activity from the old mutable timestamps. Mark backfill as a **legacy baseline**, not historical DB-observed activity. Capture one migration DB time `B`, retain all original headers/command bytes, and seed one activity at the current retained source revision. With pinned TTL `T`, select a documented finite old candidate (normally updated_at, then created_at); clamp it to `[B-T, B]`. For missing/nonfinite data use the conservative lower bound. Set `deadline = clamped_candidate + T`, so deadlines lie in `[B, B+T]`. Clamp before interval addition to avoid overflow. Record `observed_at=B`, distinct from the inferred effective activity time.

This policy expires drafts older than T immediately, retains the remaining bounded interval for recent drafts, and caps any future-dated legacy value at one full grace interval. That grace is a documented upgrade choice, not evidence the future timestamp was true. Do not manufacture past revision events or edit original timestamps. Backfill eligible retained sources, including superseded unsubmitted plans, with explicit count reconciliation; preserve protected histories and exclude already applied/submitted/physical lifecycles. Install defaults, backfill and mandatory guards atomically under the forward migration's locks so missing activity cannot become a reset window. No runtime backfill helper should remain available to app callers.

## Required proof before acceptance

Use the normal positive finite TTL model with an owner-created two-second policy version for an owned isolated test tenant, configured before creating the target after all slow setup. No test-only TTL branch, request/GUC clock override, disabled trigger or special production-guard exception. Use actual DB time and bounded polling after locks, not brittle exact sleeps.

Prove: default seven-day policy and immutable policy versions; app denial of clock/policy/activity tampering; future header/command timestamps do not extend deadlines; touch/replay/child-only/control updates do not renew; valid explicit save before expiry renews once; due save/submit/effect is denied with scheduler off; a transaction or statement begun before expiry but released from a lock after expiry fails; owner TTL increase does not revive old identities; expiry/edit and final-approval races have one valid outcome; failed/rolled-back edits leave no clock event; legacy past/future/nonfinite baselines are bounded without snapshot changes; expired latest plans do not resurrect predecessors; every retained family has consistent list/detail/filter/current-state projection and unchanged physical totals; original responses remain exact under current authorization; policy-only empty tenant deletion stays supported. Execute with warehouse_app non-owner/NOBYPASSRLS, and inspect actual results before any final review approval.
