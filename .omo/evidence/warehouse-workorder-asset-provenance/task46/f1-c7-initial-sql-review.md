## Required corrections before acceptance

**R1 — A fabricated ordinary receipt save can renew protected activity.** Sketch lines 184–207 accept `warehouse.receipt.update` using the current document revision, status 200 and response `state=DRAFT`. They do not verify resource binding, business action, response identity/revision, canonical command identity, intake or line content. The existing receipt schema has no deferred `warehouse.receipt.update` seal comparable to V178.10 transfer / V178.11 count. V174.6 only makes command identity reference an operation; it does not require every operation to have an identity. V174 permits same-state draft header revision changes, and inventory_operation's general constraints do not bind a receipt update to its content.

A scoped application writer can advance a receipt revision and insert a minimally shaped operation that satisfies this trigger. Alternatively, an actual attachment advances the header without renewing draft activity; a fabricated update operation at that revision can then satisfy `document_revision > previous.source_revision`. The unique action/revision constraint is insufficient because the sketch does not validate the action. Add a receipt-specific accepted-save structural seal, including immutable identity and exact source/response/content binding, or an equally protected admission path. A deferred structural seal may verify identity written after the operation, but must not defer the clock admission check. This is source-derived; no exploit was executed.

Evidence: `V174__warehouse_documents_and_balances.sql:67`, `:267`; `V174_6__warehouse_command_delivery_metadata.sql:1`; `V178_10__warehouse_transfer_draft_revision.sql`; `V178_11__warehouse_count_draft_revision.sql`; `WarehouseReceiptPersistence.saveDraft/advance/operation`; `ReceiptEvidenceService.kt:63`. Searching current migrations for literal `warehouse.receipt.update` found no binding.

**R2 — Raw receipt-evidence insertion bypasses expiry.** The sketch's child guards at lines 268–285 omit `inventory_receipt_evidence`. V174.12 grants the app INSERT, while its append-only protection covers UPDATE/DELETE. V174.13's BEFORE INSERT check only verifies current intake content revision/hash; it does not check draft liveness or require a header change. Therefore matching evidence metadata can be appended to an expired draft without any new activity or guarded document mutation. Add a BEFORE INSERT source-live guard using `document_id`. The API upload's later `documents.advance` will reject expiry, but that does not protect the raw child boundary.

Evidence: `V174_12__warehouse_receipt_intake.sql:12`, `:84`; `V174_13__warehouse_receipt_evidence_version.sql:30`; `ReceiptEvidenceService.kt:27`.

**R3 — Backfill has an unguarded concurrent-write window.** Lines 214–236 scan eligible existing sources before source triggers are installed at lines 238–285. No preceding lock prevents an application transaction from committing a new DRAFT after the backfill scan and before trigger installation. That source permanently lacks activity and later fails `warehouse_draft_activity_missing_ck`. A transaction around migration DDL alone does not prevent this sequence. Lock source tables and relevant accepted-save writers in a consistent order before capturing the baseline and scanning, then install/backfill atomically. Preserve fail-closed missing-activity behavior; do not repair the race with a runtime clock reset.

**R4 — Source DRAFT is not yet proven sufficient at every raw effect boundary.** Normal owner effects advance their source atomically, but the inspected SQL does not establish the inverse effect-to-POSTED invariant for TITLE_CORRECTION and ADJUSTMENT. `warehouse_assert_title_request` checks that POSTED has an effect; `warehouse_assert_title_transfer` binds effect/request/approval/movement without checking the source header's state/revision. V175.77 strengthens POSTED effect counts but remains one-way. `warehouse_assert_transfer_resolution` in V175.113.1 returns immediately for DRAFT. Generic approval posting/terminal guards bind approval and movement revisions, not current source header state. The new sketch has no liveness hook on new posting/effect insertion, and expiry/projection eligibility uses only stored DRAFT.

Do not claim all raw effects require POSTED from owner-service code alone. Seal the inverse for these families and/or explicitly reject effected/physically active sources at expiry, with a late source-live guard at new effect admission that cannot bypass the deadline after earlier approval-decision admission. Keep wall-clock checks out of deferred historical integrity validators. This is a concrete missing SQL enforcement/proof boundary, not a claimed executed counterexample. The existing default effect paths are correct about advancing their source.

Evidence: `AssetTitleCorrectionOwner.kt:45`; `WarehouseTransferApprovalOwner.kt:66`; `WarehousePostingPersistence.kt:19`, `:34`, `:38`; `V175_71__warehouse_title_approval_execution.sql:52`; `V175_73__warehouse_title_final_state.sql:34`, `:53`; `V175_76__warehouse_title_approval_snapshot.sql`; `V175_77__warehouse_title_final_seals.sql:23`; `V175_113_1__warehouse_transfer_discrepancy.sql:60`; `V175_132__warehouse_return_reacquisition_effect.sql:169` and later action extensions.

## Sound parts and bounded integration requirements

- Policy versions are immutable, pinned at creation, and bounded to positive finite TTL. The chosen seven-day default is an implementation policy, not a number dictated by C7. Clock writes use database time; client timestamps and header touches are not directly trusted. Reads and old response replay do not append activity.
- Separate document/plan activity and expiry tables have typed composite tenant references, FORCE RLS USING/WITH CHECK, finite timestamp checks, protected writes, one terminal decision per identity and no direct app INSERT/UPDATE/DELETE/TRUNCATE privileges. New functions fix `search_path` and assert scope. Policy-only tenant rows may cascade through V178.9's control-row delete guard; activity/history remain protected, matching the owner decision to suspend tenants with protected history and permit empty-tenant deletion.
- Current-state functions check persisted expiry first and otherwise compute due status without changing source snapshots. Missing eligible activity fails closed. Child/header and decision guards acquire source locks; the decision trigger sorts before the existing approval-locking trigger. Actual time is sampled after locks. Header transition in normal posting happens after stock locks, providing a late deadline boundary.
- Backfill is honestly labeled LEGACY_BASELINE, preserves original timestamps/snapshots, bounds inferred deadlines to migration time through one pinned TTL, and handles past/future/nonfinite timestamps. V174 does add created_at/updated_at to material plans, so those references are valid. R3 still needs correction.
- `*_draft_expired_at` returns the deadline before persistence, but the persisted row's observed decision time afterward. When integrating DTOs, distinguish deadline from observed terminal-record time so a displayed expiry instant does not silently change meaning. This is a projection-design note, not a migration blocker by itself.

Required later executed evidence remains: non-owner/NOBYPASSRLS tampering and raw child/effect writes; qualifying save versus no-renewal/replay/attachment/control changes; rollback preservation; pre-deadline transaction blocked until after deadline; expiry/edit/final-approval races; concurrent migration/backfill; every retained family with consistent current reads and original response replay; protected history/empty-tenant cleanup. These tests were not run by this reviewer. The initial SQL sketch is not ready for C7 acceptance until R1–R4 are resolved and the already planned integration gates pass.
