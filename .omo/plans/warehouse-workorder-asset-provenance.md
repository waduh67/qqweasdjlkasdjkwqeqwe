### Locked architecture and operational contracts

**C1 — Single ownership and module direction.** Inventory owns physical assets, warehouse documents, movements, availability, reservations, custody, material usage and asset-assignment history. Workorder owns execution/assignees/QA and provides a root `WorkOrderMaterialContextApi` read/lock contract. Customer owns the service/topology `onu` projection and its historical installation episodes. Network owns ports/topology, CPE owns ACS observations. Dependency direction: workorder -> inventory public contracts; customer -> inventory public contracts; fulfillment -> public workorder/customer/inventory/network-facing owner APIs. Inventory must not import customer/workorder/fulfillment repositories or internals. Cross-module material operations live in NEW `S/fulfillment/MaterialWorkflowService.kt`, use owner APIs, and share one local DB transaction for physical assignment + customer installation; external BNG/device calls remain outbox-driven. No second coordinator for provisioning.

Cross-owner names in inventory reports are immutable `customerLabelSnapshot`/`workOrderCodeSnapshot` captured when MaterialWorkflowService creates a document, not live reverse calls into customer/workorder. A refreshed cross-module detail is assembled in fulfillment or subscriber360 through public APIs. The old inventory-owned `POST /api/inventory/serialized/{id}/installed-onu` returns stable409 `USE_WORKORDER_ASSET_WORKFLOW`; do not make inventory import fulfillment to forward it. Customer registration routes remain customer-owned and use InventoryDeploymentApi to consume an already-issued authorization; they never call fulfillment. Discovery/AutoProvisionScheduler may call the fulfillment-owned public asset orchestration API (fulfillment must not import monitoring); the orchestrator validates WO and issue before calling CustomerAssetApi. Shared identity normalization uses a tiny common value/codec, not a customer<->inventory cycle.

Consume-time dependency inversion is mandatory: declare NEW inventory-owned root `S/inventory/InventoryWorkOrderValidationPort.kt` with `lockAndValidate(context: DeploymentValidationContext): ValidatedWorkOrderContext` using only inventory-root DTOs. Implement it in NEW `S/workorder/adapter/outbound/inventory/WorkOrderInventoryValidationAdapter.kt`, injecting workorder-owned repositories plus existing authority services, NOT InventoryDeploymentApi/WarehousePostingService/MaterialWorkflowService. Inventory's deployment consumer invokes this port in its active local transaction after cutover/current-authority fences and BEFORE locking inventory documents/stock or mutating ONU. The adapter takes the WO row lock, checks persisted actor assignment/activity/customer/action/cancel/material revisions and returns a revision-bound validated context; failure aborts the same transaction. Every consume entry, including direct CustomerController->OnuService->InventoryDeploymentApi and orchestration/discovery paths, invokes it; a pre-minted token alone never suffices. Thus static dependency stays workorder->inventory with a workorder-provided port implementation, not inventory->workorder or customer->fulfillment. Relevant existing WO mutations take that same WO lock; validation adapter must not call back into inventory commands, avoiding both module and bean-construction cycles. Direct customer endpoints may read customer identity first but must defer row mutations/locks that conflict with this order until port validation succeeds.

**C2 — Identity, stock dimensions and precision.** Reuse `inventory_serialized_asset.id` as physical assetId; never create another physical asset for return/reuse. Canonical serial = trim + locale-independent uppercase; MAC = parsed 12 uppercase hex digits, rendered with colons. Tenant-scoped canonical unique identities survive archive/disposal; collision migration reports both source rows without choosing a winner. SKU has `tracking=SERIAL|LOT|BULK`, `baseUnit=EA|MM`, allowed ownership modes and active flag. Device base quantity is exactly 1. Cable internal quantities use checked signed 64-bit integer millimetres (`bigint`), APIs use base quantity integer strings and display metre decimal strings (0-3 fractional digits, reject excess precision/overflow). Package conversions are positive rational integer ratios snapshotted per receipt, not mutable historic conversions. A reel/lot contains measurable quantity; returned cut segments keep parent lineage and physical segment identity, not fictitious contiguous cable on the original reel. GIS cable length remains an estimate, never rewrites stock.

Separate `location`, `custodian`, `condition=SERVICEABLE|QUARANTINE|DAMAGED|SCRAP`, and `legalOwner=ISP|CUSTOMER|UNKNOWN` from reservation. Customer-owned RMA and legacy-unknown stock is counted separately and excluded from ISP available stock. Available = serviceable physical quantity in issue-eligible bins minus open reservations; transit, picked allocations, provisional installation and quarantine are unavailable. One serialized asset has one active physical position and at most one active customer assignment.

Every measurable physical piece has `stockIdentityId`: a serialized asset for EA, a reel/cut/remnant segment for MM, or a bulk-lot stock identity for fungible EA. MM demand lines have `continuousCut=true` by default; splitting one required cut across pieces requires an explicit revised demand. Picking100m from a1000m reel atomically retires the parent spendable segment and creates child100m+900m identities with equal quantity, transfers reservations onto the correct children, and records split lineage. Installation of82.5m similarly splits the issued100m into used82.5m and remnant17.5m. Picking never creates a second reservation or subtracts it twice: `reserved_unpicked + reserved_picked` is one encumbrance, dispatch consumes that encumbrance and moves physical quantity. Two10m remnants cannot satisfy a continuous15m cut. Segment identity participates in every lock/balance/reservation/movement/count key; lotId alone is not sufficient.

**C3 — Posting and concurrency.** A single NEW `WarehousePostingService` replaces all production in-memory ledger/fact/approval mutations and direct durable-fulfillment leg insertion. Command transaction commits document revision, immutable movement header/paired legs, checked balances, reservation deltas, asset custody, usage facts, immutable original response, and outbox. Reserve/release are availability events, not physical IN/OUT. A stock transfer has equal OUT/IN base units and one business document. Consumption moves issued quantity into an explicit consumed sink, so it is not deducted twice from the originating warehouse. All balance dimensions include tenant/SKU/stockIdentityId/lotId-if-applicable/location/custodian/condition/owner. Locked zero-balance rows are inserted under a unique dimension constraint before arithmetic; global lock order is tenant-cutover fence, current-authority fence, WO context, inventory document/assignment, then deterministic stock-dimension keys. Serializable/retry or row-lock conflict maps to stable409; never oversell on missing-row races.

Mutating API requests require `Idempotency-Key` plus expected document revision for existing resources; tenant/actor come from authentication. Server computes canonical payload hash, including stable referenced document versions, not current mutable lookups. Unique `(tenant, namespace, key)` and unique `(tenant, document, businessAction, documentRevision)` prevent duplicate postings even with a new key. Same command replays the original status/body; changed payload gives 409. Posted rows, identity, unit/cost/approval snapshots and stock audit are append-only; compensation is a new linked document. Inbox receipt and consumer effects commit together. Retry after DB commit/HTTP response loss must be covered. WMS mutation failures cannot quietly succeed or return empty lists as a fallback.

Operation rows bind the original actor and resource scope as well as the key/hash. Check current authorization BEFORE returning stored responses: same user with fresh permitted session can replay; another actor cannot obtain the response just by guessing a key, and a revoked actor cannot recover private results via replay. Authorization failure returns403/indistinguishable404 without executing or returning prior payload.

**C4 — Document states.** Masters are ACTIVE/ARCHIVED (no archive while balances/open references exist). Receipt DRAFT -> RECEIVED_IN_INSPECTION -> PUTAWAY/CLOSED; accepted quantities may bypass separate inspection only for SKU policies that explicitly permit it. Rejected quantities remain supplier-return/quarantine, not available. Transfer DRAFT -> DISPATCHED -> PART_RECEIVED -> RECEIVED or DISCREPANCY; remainder stays IN_TRANSIT. Demand DRAFT -> SUBMITTED -> PART_RESERVED/RESERVED -> PART_ISSUED/ISSUED -> SETTLING -> CLOSED, or CANCELLED only for unissued demand; keep quantitative line totals rather than infer them from a single status. Issue DRAFT -> PICKED -> DISPATCHED -> PART_RECEIVED/RECEIVED; handover tracks sender/receiver and rejection/missing quantities. Same-person physical issue/receipt may be allowed by normal job permissions but never substitutes for independent exception approval. Reservations default expiry = max(submission + 24h, scheduled WO end + 24h); extension is dispatcher-authorized and audited; only unissued/unpicked quantities expire automatically. Picked goods first require an explicit unpick to return availability.

Return DRAFT -> DISPATCHED -> RECEIVED_IN_INSPECTION -> ACCEPTED/REPAIR/SUPPLIER_RETURN/SCRAP; inspection receipt does not automatically make goods serviceable. Repair records outbound custody, vendor/reference, result and inspected return; replacing equipment yields a distinct physical asset only if it actually is a different device. Count DRAFT -> COUNTING -> SUBMITTED -> APPROVED -> POSTED or RECOUNT_REQUIRED. Freeze only the observed dimension revision, not the whole warehouse: intervening movement makes posting stale (409) and requires recount, checked again at approval execution. Loss/scrap/adjustment require document-bound independent approval, never negative stock as a substitute.

**C5 — WO and physical usage.** Existing WO retains its lifecycle. Material plan is a versioned BOM/demand snapshot (templates per work type, optional defaults, explicit SKU choices). Partial supply/backorders and explicit authorized SKU substitutions are supported. Materialless jobs explicitly declare `materialMode=NONE` and reason; absence of allocations in MATERIAL_REQUIRED mode is an error. Standalone network/preventive WO does not need fabricated customer/subscription. Items may be supplied from an approved warehouse or named technician stock, always with traceable allocation. Reassignment does not transfer physical custody; old custodian can return or hand over outstanding goods but cannot post new use on a revoked assignment.

Physical `report-use` atomically posts actual consumption/deployment and its immutable revision before QA; installed/consumed goods become unavailable immediately. It only spends acknowledged issue lines and cannot exceed remaining quantities. A returned/remnant/scrap quantity is a separate disposition, with `issued = physically-used + returned + transferred-out + disposed + still-accountable` in base units. QA approves a frozen use/installation snapshot and never posts that consumption again. Reject/resubmit creates corrected revisions/compensations, never pretends installed hardware returned. Approval material effect becomes SETTLEMENT_VERIFY against referenced postings; remove legacy consume-on-approval path for new material documents. All effect applicability is server-derived per explicit links and actions: MATERIAL settlement when required; CUSTOMER/ONU assignment if present; subscription/provisioning only when job truly changes service; ORDER/VISIT only when linked. Empty effects never invoke legacy activation. Installation, QA, provisioning and residual material settlement remain visible independent statuses. Service may finalize after approved used-material evidence while unused stock remains a visible return obligation; material settlement closes only when every residual is returned, transferred/reallocated or disposed with authorization.

**C6 — Customer equipment, loan/sale and bypass prevention.** Physical asset origin must be verified RECEIPT or approved physical OPENING_BALANCE. New assignment requires an acknowledged issue, matched customer/WO/technician and immutable assetId. Serial-only lookup is discovery/search, not assignment authority. Inventory persists `inventory_asset_assignment` episodes; customer preserves one `onu` service-installation episode per deployment and adds assetId/assignmentId/retiredAt. Existing IDs remain stable; reuse for a different customer creates a new ONU episode, never changes the customer of old telemetry/history. Change serial uniqueness to one active normalized serial per tenant, with separate physical-asset unique identity. Current operations resolve the active episode; historical observations use the time-aware attribution below. A customer can have multiple devices. Generic customer equipment (routers etc.) uses the assignment projection without requiring an ONU topology row.

All registration/provisioning paths (CustomerController -> OnuService; CustomerApiService.provisionOnu; DiscoveredOnuService; AutoProvisionScheduler; future imports using those APIs) must pass the same InventoryDeploymentAuthorization gate. A persisted deployment authorization binds tenant, asset, issue line, WO, customer, actor, purpose, expected revisions and a stable operation ID; it is consumed in the same local transaction as the assignment and customer episode. No HTTP field such as `legacy=true`, actorId, tenantId or arbitrary external source may mint it. Discovery ingestion remains observations only; unknown/unissued serial stays awaiting reconciliation, never creates stock. Existing known active installations still accept telemetry and non-ownership topology observations.

LOAN remains ISP-owned and creates a recovery obligation on service termination; SALE is initially sale intent. An explicit customer handover/acceptance event linked to asset/WO finalizes title transfer to CUSTOMER, independent of QA. No invoice, tax, payment or refund is created by that choice. A sold-device RMA remains CUSTOMER-owned and cannot be reissued; reacquisition requires independent approval and title-transfer evidence before inspection can release ISP stock. No BYOD path. Legacy unknown devices remain readable/operational with provenance UNKNOWN and cannot be moved to a new customer or normal available stock until privileged reconciliation proves origin/ownership. Physical retrieval into quarantine is allowed, but does not itself prove title.

An inspected repaired RMA may be returned to its ORIGINAL customer through a purpose-bound `RETURN_CUSTOMER_RMA` authorization referencing the prior warehouse-origin asset, original owner, repair case and return handover. This is not a new sale, BYOD intake or issue from ISP available stock; title stays CUSTOMER throughout. Returning it to another customer requires explicit reacquisition and normal warehouse issue, never reuse of this exception. Reserve expiry uses scheduled WO end where present, otherwise scheduledAt; if neither exists use submission+24h as C4 fallback.

Swap locally closes the old active assignment and opens the new one with an old/new immutable relation; old physical device moves to recovery custody, not available stock. Distinct outbox provisioning success/failure never erases physical facts. Dismantle records actual removal before return; topology detach/ODP relocation alone never restocks. Customer/ONU delete is blocked with active assignments/open custody; historical records are retired/anonymized under existing retention policy, not cascade-deleted into dangling inventory pointers.

Observation attribution is not active-only lookup. Episodes use server-recorded half-open intervals `[startedAt, endedAt)`. Add CustomerApi lookup for serial+observedAt+device/path context; server-side poll samples use server clock, authenticated collector samples must pass existing validation plus bounded skew/age checks (default future tolerance5min, maximum age72h) before attribution. A delayed valid sample from episode A is associated only with A, never current episode B; historical ingestion cannot update B live status/alarms. Ambiguous/untrusted/unmatched timestamps remain tenant-scoped unassigned observations with a reason. CPE/ACS binding stores assignment/episode revision; on reassignment invalidate the previous customer-visible snapshot and require fresh Inform/readback timestamp after new episode start before exposing fields to B. Do not reparent old cached ACS data or telemetry rows. Tests cover A->return->B followed by a previously unseen delayed A batch and stale ACS poll.

**C7 — Security and control.** Use existing three-part permission grammar. New families: `inventory.sku.{view,manage}`, `inventory.receipt.{view,manage}`, `inventory.request.{view,manage}`, `inventory.issue.{view,manage}`, `inventory.transfer.{view,manage}`, `inventory.return.{view,manage}`, `inventory.count.{view,manage}`, `inventory.report.view`, `inventory.cost.view`, `inventory.provenance.{view,manage}`, retaining location/item/custody and approval families. Field actions require WO field permission AND current assignment plus owned custody; approver-only routes need approval.view, not item.view. All rows have immutable tenant_id, FORCE RLS USING/WITH CHECK, composite tenant FKs, indexes, unique business identities and lifecycle constraints; application test user must be non-owner and NOBYPASSRLS. Scope includes permitted warehouses and WO area. Server-owned versioned approval policies derive requester, value, tiers, expirations and effect target; no request-defined approvers, hashes or movementId override. Requester/custodian/counter and delegated versions cannot self-approve; platform privilege cannot waive these invariants. Missing independent approver or unknown cost needed for a value threshold blocks posting with an actionable setup reason, never assumes zero. Ordinary receiving/in-policy issue uses granted role permissions; exceptions require approval. Idle drafts expire without stock effects. Audit is redacted and append-only; attachment/proof uses existing secured object storage, not public uploads.

Current-authority protocol: add IAM-owned root `CurrentAuthorityApi` and a tenant authorization-epoch row. WMS commands obtain a shared transactional fence and reload enabled user, effective roles/permissions/areas plus current inventory warehouse scopes; JWT identifies the user but is not sole authority. User disable, role grants, user-role/area assignment and warehouse-scope/delegation changes acquire the same fence exclusively and increment the epoch in their transaction; inventory may depend on IAM/common public security contracts, never the reverse. Update every existing WO assign/update/cancel/complete/approve/reject command to take the WO context lock/revision in the global order. Minted deployment authorization stores epoch and WO/material/issue revisions; consumption reloads and compares all of them under locks, failing stale authorizations before stock/ONU writes. Lock protocol lasts through local DB commit, never an external provisioning call. A successful earlier transaction is not retroactively undone by a later revocation; an authorization consumed after revocation is denied. Tests must pause mint/consume and revoke/reassign from a second real transaction using the original JWT.

Barcode scanner keyboard input and camera scan where supported both use exact serial lookup; manual entry always available and scan alone never commits.

Existing read response fields remain; asset/provenance fields are additive.
